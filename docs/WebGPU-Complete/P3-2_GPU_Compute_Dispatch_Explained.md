This is the comprehensive technical specification for **The Runtime Loop: The Compute Dispatch**.

This document defines the core "heartbeat" of the instrument. It details exactly how the CPU triggers the GPU to execute the physics simulation, how the workload is distributed across thousands of threads, and the strict logic flow within the shader to ensure data consistency.

# The Runtime Loop: The Compute Dispatch

**Objective:** Execute the entire graph's logic (Physics, Logic, Animation) for the current frame.

**Invariant:** The simulation must advance by exactly one time step (\$dt\$) across all active instances.

**Mechanism:** A single dispatchWorkgroups call that launches thousands of threads, organized into local workgroups, executing the "Uber-Shader" generated by the compiler.

## 1. The Dispatch Geometry (The Math)

The GPU does not execute "one thread per particle" directly. It executes **Workgroups**.

- **Workgroup Size:** Fixed at **64**.

  - *Why 64?* It aligns with the "Wavefront" size on AMD (64) and is a multiple of the "Warp" size on NVIDIA (32). It is the "Goldilocks" number for occupancy.

- **Instance Count (\$N\$):** The total number of active elements in the largest field (e.g., 10,000 particles).

### 1.1 The Calculation

The CPU calculates the dispatch size every frame:

\$\$GroupCount = \lceil \frac{\text{InstanceCount}}{64} \rceil\$\$

- *Example:* For 10,000 particles:\
  \$\$10000 / 64 = 156.25 \rightarrow \textbf{157 Workgroups}\$\$

- *Result:* The GPU launches \$157 \times 64 = 10,048\$ threads.

- *The Tail:* The last 48 threads are "Overshoot." The shader must handle this (see Section 5).

## 2. The Pipeline Interface (GPUBindGroup)

Before dispatch, the RuntimeExecutor binds the resources. There is typically only **Layout Group 0**.

| **Binding** | **Resource** | **Type** | **Access** | **Description** |
|----|----|----|----|----|
| **0** | Arena_Read | storage | read | The state from Frame \$N-1\$ (Inputs). |
| **1** | Arena_Write | storage | read_write | The destination for Frame \$N\$ (Outputs). |
| **2** | Shape_Bank | storage | read | Static topology definitions. |
| **3** | Textures | texture_2d | sample | (Optional) Array of user loaded images. |
| **4** | Sampler | sampler | \- | Standard linear sampler. |

### 2.1 The "Ping-Pong" Bind Logic

- **Frame Even:** Bind Arena_A to Slot 0, Arena_B to Slot 1.

- **Frame Odd:** Bind Arena_B to Slot 0, Arena_A to Slot 1.

- *Crucial Check:* Ensure the Arena_Write buffer has usage STORAGE \| COPY_SRC.

## 3. The Kernel Anatomy (Inside the Shader)

The compiler generates a single main function. This function has a strict execution order to prevent dependency violations.

Code snippet

@compute @workgroup_size(64, 1, 1)\
fn main(@builtin(global_invocation_id) global_id: vec3\<u32\>) {\
let lane = global_id.x;\
let total_instances = arrayLength(&arena_in) / STRIDE; // Simplification\
\
// --- PHASE 1: SCALAR EXECUTION (The "Brain") ---\
// Every thread calculates scalars (LFOs, Math) locally in registers.\
// This redundancy is cheaper than barrier synchronization.\
\
let lfo_1 = sin(uniforms.time);\
let math_res = lfo_1 \* 0.5;\
\
// WRITER LOCK: Only Thread 0 writes scalars to memory.\
// This prevents race conditions where 10,000 threads write to address 5.\
if (lane == 0u) {\
arena_out\[SCALAR_OFFSET + 0\] = lfo_1;\
arena_out\[SCALAR_OFFSET + 1\] = math_res;\
}\
\
// --- PHASE 2: GUARD (The "Tail" Check) ---\
if (lane \>= MAX_INSTANCES) {\
return;\
}\
\
// --- PHASE 3: FIELD EXECUTION (The "Muscle") ---\
// Read -\> Compute -\> Write\
\
// 3.1 Input Read (Coalesced)\
let pos_x = arena_in\[FIELD_OFFSET_X + lane\];\
let pos_y = arena_in\[FIELD_OFFSET_Y + lane\];\
\
// 3.2 Logic (The Graph)\
let new_x = pos_x + (math_res \* 0.1); // Use scalar from Phase 1\
let new_y = pos_y + 0.01;\
\
// 3.3 State Update\
arena_out\[FIELD_OFFSET_X + lane\] = new_x;\
arena_out\[FIELD_OFFSET_Y + lane\] = new_y;\
}

## 4. The Execution Phases

### Phase 1: Scalar Evaluation (Redundant Compute)

- **The Logic:** LFOs and global variables are computed by **all threads**.

- **Why:** Register access is instant. Reading a scalar from shared memory (after a barrier) takes cycles. For small graphs (\<500 nodes), redundant calculation is faster than synchronization.

- **The Write Guard:** We use if (global_id.x == 0) to ensure only the first thread writes the scalar results to the Arena_Write buffer. This protects the memory controller from 10,000 simultaneous writes to the same address.

### Phase 2: The Tail Guard

- **The Problem:** We launched 10,048 threads for 10,000 particles. Threads 10,000 to 10,047 are processing garbage memory.

- **The Fix:** if (global_id.x \>= instance_count) { return; }

- **Placement:** This check must happen **after** Scalar Phase (because Thread 0 is always valid) but **before** Field Phase (to prevent out-of-bounds reads).

### Phase 3: Field Evaluation (SoA)

- **The Workhorse:** This is where 99% of the GPU time is spent.

- **Memory Access:** Because of the **SoA** layout, Thread \$N\$ reads address \$Base + N\$, and Thread \$N+1\$ reads \$Base + N + 1\$. This is a **Coalesced Memory Access**, allowing the GPU to fetch 128 bytes in a single transaction.

## 5. Handling Feedback (State)

What if a particle needs to know its *neighbor's* position (e.g., a trailing effect)?

### 5.1 The "Read-Only" Rule

Threads can read *any* index from Arena_Read.

- let neighbor_val = arena_in\[OFFSET + lane - 1\];

- *Constraint:* You are reading the neighbor's state from **Frame N-1**. You cannot read the neighbor's "New" state (Frame N) because the neighbor might not have run yet.

### 5.2 The "Atomic" Exception

If you need to accumulate values (e.g., "Count how many particles are inside the circle"), you cannot use standard arrays.

- **Mechanism:** Use a dedicated atomic\<u32\> buffer zone.

- **Operation:** atomicAdd(&arena_out\[COUNTER_OFFSET\], 1u);

- *Warning:* Atomics serialize execution. Use sparingly.

## 6. Optimization: The "Active Count"

For v3.0, we dispatch based on the **Capacity** (Maximum Allocated Particles), not the **Active Count** (Alive Particles).

- **Why:** If the buffer holds 100,000 slots but only 5 are alive, dispatching 100,000 threads is wasteful.

- **Optimization (Future):** Use dispatchIndirect.

  - A small compute shader writes the ActiveCount to an indirect buffer.

  - The main dispatch uses that buffer.

- **Phase 0 Decision:** Stick to CPU-side dispatch(MaxCapacity). It is simpler to debug. If performance suffers, we implement Indirect Dispatch in v3.1.

## 7. Summary of Implementation

1.  **Update RuntimeExecutor:** Calculate workgroup_count = ceil(capacity / 64).

2.  **Update Shader Gen:** Inject the if (lane == 0) guard around scalar writes.

3.  **Update Shader Gen:** Inject the if (lane \>= capacity) return; guard before field logic.

4.  **Verify Bindings:** Ensure Arena_Read and Arena_Write are bound correctly for the current frame index.

This dispatch model ensures that your physics engine scales linearly with GPU power. A 10,000 particle system that runs at 60fps on a laptop will run at 1000fps on a desktop, with zero code changes.
